# 14 - 技术决策与取舍

> 明确边界：重点做到哪些能力，简化哪些部分，放弃哪些部分

---

## 一、为什么需要这篇文档

题目要求很明确：**个人独立**完成，**6 天**时间，**不允许用 agent 框架/SDK**。面试环节评委只关注一件事——

> "你是否理解你的 agent 为什么这样运转，是否能为你的设计决策给出辩护。"

也就是说，评委不是在看功能清单有多长，而是在看每一个"做"和"不做"背后有没有想清楚。这篇文档就是把取舍逐条写清楚，既是给自己的开发纪律（防止范围蔓延），也是面试时的答辩底稿。

判断依据主要来自实际读过源码的 5 个参考项目：**pi**（Earendil）、**claude-code**（Anthropic）、**claw-code**（Rust 实现）、**deepseek-harness**（DeepSeek）、**opencode-dev**（SST）。这些是团队级、长期维护的项目，功能天然比我们全，但正因为看过它们的完整形态，才更清楚哪些是"编程 Agent 的本质"，哪些是"团队产品才需要的外围能力"。

---

## 二、决策框架：三个问题

对每一个候选功能，依次问：

1. **它是不是题目要求的核心能力？**（对话历史与上下文管理、工具的定义与本地执行、模型输出解析、循环终止条件、错误处理——题目原文列出的 5 项）
2. **5 个参考项目里，这是共识（大家都做/都不做），还是分歧？** 共识意味着这是"没有它就不算数"或者"大家都放弃了说明性价比低"。
3. **单人 6 天内，能不能做到"完整且讲得清楚"，而不是"看起来有但一碰就露馅"？** 半成品比不做更危险——面试会被追问细节。

下面的分类就是这三个问题的答案。

---

## 三、必须做到的核心能力（P0）

这些是题目原文点名要求的，也是 5 个项目无一例外都有的最小内核。

| 能力 | 为什么必须做 | 参考依据 |
|------|-------------|---------|
| Agent 主循环（ReAct：调用 LLM → 执行工具 → 判断继续/结束） | 题目要求"循环终止条件"，是 Agent 的骨架 | pi/claw-code 的循环结构最简洁，作为主要参照 |
| 工具系统（读写文件、执行命令，本地实现） | 题目明确要求"工具的定义与本地执行"，且**禁止**用服务端托管的 Code Interpreter/Files API | 5 个项目工具集合高度一致：read/write/edit + bash + 搜索 |
| LLM 接口层（至少 1 个 provider，支持流式和 tool calling） | 没有这一层 Agent 无法运转 | pi 的 Provider 统一抽象最值得借鉴 |
| 树形对话历史（parent 指针） | 题目要求"对话历史与上下文管理"；树形结构是本项目的差异化亮点，不是可选项 | deepseek-harness 是唯一实现完整树形+分支的项目，证明这条路可行但复杂度不低 |
| 错误处理（工具错误不中断 / API 错误中断的边界） | 题目明确要求 | claw-code 的错误边界最清晰，直接采用 |
| 模型输出解析（tool_calls 解析、流式增量拼接） | 题目明确要求 | 所有项目都有，做法趋同 |

这 6 项没有讨价还价的空间，是评委面试时最可能深挖的部分。

## 四、简化的部分（做，但做减法）

以下功能确实需要，但参考项目的实现复杂度远超单人 6 天能负担的程度，做"够用版"而不是"完整版"。

### 4.1 Lane 分支管理 → 只做核心操作

**参考项目的复杂度**：deepseek-harness 的 Lane/分支系统支持智能命名建议、复杂 diff 视图、多级 rebase。

**我们的简化**：只做 `create_lane` / `switch_lane` / `list_lanes` 三个操作 + 基于 parent 指针的公共祖先查找。不做智能命名（省去一次额外的 LLM 调用），不做逐字符 diff 视图（用简单的"两个分支各自的消息列表并排展示"代替）。

**理由**：分支管理的核心价值是"无损探索多方案"，这一点用最简操作就能体现；花时间在命名建议或精细 diff 上，边际收益低。

### 4.2 权限控制 → 3 级模型，不做规则引擎

**参考项目的复杂度**：claw-code 有完整的 `allow_rules` / `deny_rules` / `ask_rules` 通配符匹配引擎。

**我们的简化**：固定的 3 级权限（SAFE 自动执行 / WRITE 提示确认 / DANGEROUS 强制确认），权限与工具绑定是硬编码的，不支持用户自定义规则表达式。

**理由**：规则引擎是"可配置性"需求，比赛场景下只需要"证明我知道要分级管控风险"，不需要真的让用户写规则。

### 4.3 沙箱隔离 → 不做容器化，只做进程约束 + 权限闸门

**参考项目的复杂度**：claude-code、claw-code 都有生产级 Docker 隔离（cap_drop、网络隔离、seccomp、资源限额）。

**我们的简化**：不引入 Docker。风险本来就只集中在命令执行这一个工具上（read/write 靠路径校验，联网搜索靠内容标记，都不需要"隔离"），用两层轻量防线覆盖：① 权限确认闸门——危险命令模式匹配 + DANGEROUS 级强制用户确认；② 进程级约束——固定工作目录、超时终止、禁用 `shell=True` 避免注入。详见 [10-沙箱隔离](../04-支撑模块/10-沙箱隔离.md)。

**理由**：威胁模型是"自己的 Agent 在自己机器上偶尔判断失误"，不是"防护大量陌生用户/不可信代码"，容器隔离防的是发生概率很低的极端场景。Windows 环境下引入 Docker Desktop/WSL2 依赖，反而会给演示录像增加新的失败点（镜像没预热、容器起不来）。命令执行器接口与实现分离（`run_command(cmd, workspace, timeout)`），未来要换成容器实现也不影响调用方，但本次不做。

### 4.4 日志系统 → 结构化记录，不做实时监控面板

**简化**：JSONL 落盘 + WebSocket 推送到前端即可，不做类似 Grafana 那种指标聚合/告警面板。

**理由**：日志的作用是"演示时能看到 Agent 在想什么、做什么"，追加写 + 实时推送已经足够，不需要额外的监控基础设施。

## 五、放弃的部分（不做，且说明为什么）

以下是经过对比后**主动放弃**的功能，不是"没想到"，是判断过后不划算。

### 5.1 RAG / 向量检索

**决策：不做。**

**依据**：查过 5 个项目的源码，**没有一个做向量 embedding 检索**。搜索 `vector`、`embedding`、`semantic search` 关键词，命中的全是无关文本。它们对"代码检索"的统一做法是**实时 grep/glob**（deepseek-harness 的 `tool-fs-search`、claude-code 的 `grep_search`/`glob_search`、claw-code 同款）。

**理由**：代码库检索场景下，关键词/符号匹配比语义向量更精确（函数名、变量名是精确字符串,不需要语义相似度），而且向量方案需要预建索引、维护增量更新，成本远高于收益。让 LLM 自主调用 grep/glob 按需检索，是行业共识，不是我们能力不够才放弃。

### 5.2 MCP（Model Context Protocol）

**决策：不做，但工具注册表设计上留扩展点。**

**依据**：claude-code、claw-code、deepseek-harness、opencode-dev 都实现了完整 MCP client（stdio JSON-RPC 或多种传输）。但 **pi 明确选择不做**，官方原话：

> "It intentionally does not include built-in MCP, sub-agents, permission popups, plan mode, to-dos, or background bash."

pi 的态度是把这些推给 extension/package,保持核心极简。

**理由**：MCP 的价值是"接入外部工具生态"（GitHub、Asana 等第三方服务）。我们的场景是一个独立的编程 Agent 演示，没有外部工具生态需求，做 MCP client 意味着实现一套 JSON-RPC 通信协议,纯粹是协议适配的工作量，不体现 Agent 本身的设计能力。工具注册表（`ToolRegistry`）按接口而非实现耦合设计，理论上以后可以接入 MCP，但不在本次范围内。

### 5.3 复杂技能引擎（Skills）

**决策：不做完整引擎，最多做 1-2 个硬编码的快捷指令。**

**依据**：deepseek-harness 的 `SkillRegistry` 支持多 provider（文件系统/HTTP/插件数据）、按 scope 分层覆盖、model-invocable/user-invocable 策略分离，工程量很大；claude-code 的 `SKILL.md` + 三层渐进式披露也是一套完整的资源加载系统。

**理由**：Skills 本质是"预定义的复杂操作链"，对我们的核心亮点（树形历史+分支）没有增益，纯粹是额外的框架代码。如果时间允许，最多加一两个写死的快捷操作（比如输入 `/test` 直接触发一段固定 prompt），不做成通用引擎。

### 5.4 项目级指令文件（类似 AGENTS.md）

**决策：放弃，判定为"低成本但非必要"。**

**依据**：pi、deepseek-harness、claw-code、opencode-dev 全部都有 `AGENTS.md`,做法趋同——一个 Markdown 文件放项目根目录，启动时读进 system prompt。

**理由**：这个功能实现成本确实很低（几行代码：读文件塞进 system prompt），但它解决的是"团队协作中统一 Agent 行为"的问题,单人比赛项目没有这个场景，加了也无法在 2 分钟演示视频里体现价值。明确放弃而不是含糊地"有时间再做"，避免它占用本该花在核心亮点上的时间。

### 5.5 插件化架构

**决策：不做。**

**依据**：deepseek-harness 基于 Cordis 框架做到"一切皆插件"，opencode-dev 用 Effect-TS 做事件溯源+插件化。

**理由**：插件化解决的是"第三方开发者扩展"的问题，需要设计稳定的插件协议、生命周期管理、依赖注入容器,学习成本和实现成本都远超收益。工具系统用简单的注册表模式（`ToolRegistry.register()`）完全够用，功能模块直接 import，不做动态加载。

### 5.6 多 LLM Provider 全面支持

**决策：只做 1-2 个 provider，不追求"支持所有模型"。**

**理由**：pi 的"自动生成模型列表"（从各 Provider API 拉取最新模型）是团队长期维护才有意义的功能。我们只需要证明"LLM 接口层做了 Provider 抽象"，接入 OpenAI 和 DeepSeek 两家（都兼容 OpenAI 协议）即可验证抽象是合理的，不需要真的适配 5+ 家。

### 5.7 CLI/TUI

**决策：不做独立 CLI 产品化，只保留最简调试用命令行入口。**

**理由**：树形历史需要可视化才能体现价值，Web UI 是必选项。CLI/TUI（如 pi 的终端界面）需要额外的渲染引擎和交互处理,和 Web UI 是两套完全不同的前端工作量，单人时间下必须二选一。

## 六、如果时间超支：砍功能的顺序

这是一份应急预案。按顺序，越靠后越不能动：

1. **先砍 Web UI 的视觉打磨**——动画、过渡效果可以退化为静态切换,但树形图和分支切换的基本交互不能砍。
2. **再砍 Lane 的分支对比可视化**——退化为"只能创建/切换分支，看不到并排 diff"。
3. **再砍进程约束的完善程度**（超时、cwd 限制本身不砍，只是简化实现，比如不做内存/CPU 精细限额）——沙箱本来就没有 Docker 路径，这里砍的是"锦上添花"的资源监控。
4. **再砍日志系统的实时推送**——退化为只写 JSONL 文件，不做 WebSocket 实时展示。
5. **最后才能考虑精简 P0**——但树形历史、Agent 主循环、工具系统、LLM 接口、错误处理这 5 项原则上不砍,因为这是评委面试时的提问核心，砍了等于放弃题目要求。

## 七、面试环节的预期问答

评委大概率会问"为什么不做 X"，这里预先列出答案要点（对应第五节的详细论证）：

| 可能被问到的问题 | 一句话答案要点 |
|-----------------|---------------|
| 为什么不做 RAG / 向量检索？ | 查过的 5 个主流编程 Agent 都没做，代码检索场景关键词匹配比语义向量更精确，grep/glob 按需检索是行业共识 |
| 为什么不接入 MCP？ | MCP 解决的是外部工具生态接入，我们没有这个场景；pi 同样主动放弃，保持核心极简 |
| 为什么用树形历史而不是线性历史？ | 线性历史无法支持"无损探索多方案"，parent 指针实现代价可控，且是本项目的差异化定位 |
| 为什么用 JSONL 不用数据库？ | 追加友好、崩溃恢复好、可读性强（演示可直接展示文件内容），查询模式简单不需要 SQL 的灵活性 |
| 为什么权限模型只有 3 级，不支持自定义规则？ | 3 级模型已经能体现"风险分级管控"的设计意图，规则引擎是可配置性需求，不是核心能力证明 |
| 为什么不用 Docker 做沙箱隔离？ | 风险只集中在命令执行工具上，权限确认闸门 + 进程级约束（cwd/超时/禁 shell）已覆盖"自用场景下 LLM 判断失误"这个真实威胁；容器隔离防的是不可信第三方代码场景，与本项目威胁模型不符，且 Windows 下引入 Docker 依赖对演示反而是新风险点 |
