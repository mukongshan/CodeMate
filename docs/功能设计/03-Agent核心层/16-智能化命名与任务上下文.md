# 16 - 智能化命名与任务上下文

> 当前实现基线：2026-09-02
>
> 为 Session、Lane 和后续任务管理提供可控的智能元数据能力。本功能已经接入 SessionRuntime、REST API 和工作台。

## 一、目标与范围

当前 CodeMate 已经能够保存树形对话、切换 Lane、执行工具和恢复上下文；Session 和 Lane 的智能命名已经作为可失败的增强能力落地。Session 仍以 ID 作为无标题初始值，Lane 仍以安全 slug 作为兼容身份。

本阶段包含：

| 能力 | 说明 |
|---|---|
| Session 自动命名 | 首轮用户需求完成后生成简短标题；用户手动命名后不再覆盖 |
| Lane 命名建议 | 根据当前会话上下文和用户意图生成多个名称、展示名和描述候选 |
| Lane 元数据 | 保留兼容现有 slug，同时增加展示名和名称来源 |
| 前端同步 | 工作台显示 Session 标题和 Lane 展示名；跨窗口操作通过 WebSocket 刷新 |
| 失败降级 | LLM 不可用时使用本地规则生成标题或候选，不阻塞主任务 |

本阶段不改变 `Entry.parent` 树查询规则、不改变 Git worktree 的目录策略，也不把用户可读名称直接用于 Git 分支路径。

## 二、设计原则

1. **用户控制优先**：显式输入的 Session 标题或 Lane 名称优先级最高，自动命名不能覆盖。
2. **兼容优先**：现有 `lane` 字段继续作为安全 slug、API 路径和 Git 标识，已有 JSONL 数据无需迁移即可加载。
3. **异步增强**：命名请求不是 Agent 主循环的一部分；命名失败不能导致任务失败。
4. **可解释**：保存名称来源 `manual`、`auto`、`fallback` 或 `default`，便于 UI 和后续策略判断。
5. **确定性降级**：同一输入在本地降级时得到稳定、可预测的结果，并且始终经过后端规则校验。

## 三、元数据模型

### 3.1 Session 元数据

Session 的 `session.json` 增加以下字段，旧文件缺失时使用默认值：

| 字段 | 类型 | 默认值 | 含义 |
|---|---|---|---|
| `title` | string | Session ID | 当前展示标题 |
| `title_source` | string | `default` | `default`、`auto`、`fallback` 或 `manual` |
| `title_locked` | boolean | false | 用户显式命名后锁定自动更新 |
| `title_updated_at` | number/null | null | 最近一次标题更新的 Unix 时间戳 |

创建 Session 时传入 `title` 即视为手动标题并锁定。未传入标题时先使用 Session ID；首轮消息结束后才进行自动命名，避免创建页面等待 LLM。

### 3.2 Lane 元数据

`LanePointer` 保留原有字段，并增加：

| 字段 | 类型 | 默认值 | 含义 |
|---|---|---|---|
| `lane` | string | - | 兼容字段；继续作为 kebab-case slug、API 路径和 Git 标识 |
| `display_name` | string | `lane` | 面向用户显示的名称，可包含中文 |
| `name_source` | string | `manual` | `manual`、`auto` 或 `fallback` |
| `description` | string | 空字符串 | 该 Lane 要验证的方案或目标 |

本阶段不立即把所有引用从 `lane` 迁移到 `lane_id`。`lane_id` 继续作为已有稳定身份字段，后续可以在不影响 URL 和 Git 的前提下完成内部引用解耦。

## 四、Session 自动命名流程

1. 用户创建无标题 Session，服务端写入 `title_source=default`、`title_locked=false`。
2. 用户发送首条消息，正常进入 Agent 主循环；消息内容仍然是唯一的任务输入来源。
3. Agent 运行结束并释放运行锁后，若标题未锁定且仍为 `default`，NamingService 在独立后台任务中使用本次用户需求和最终回复生成标题；该任务不计入 Agent 运行态。Session 删除或运行时清理时会取消该后台任务。
4. LLM 输出必须是包含 `title` 字段的 JSON 对象；服务端清理 Markdown、换行和过长内容后再保存。
5. LLM 调用失败、超时或输出非法时，使用本地规则从用户需求中截取稳定标题，并将来源标记为 `fallback`。
6. 保存成功后推送 `session_title_updated`，前端立即更新工作台标题；其他窗口通过自己的 WebSocket 收到同一事件。
7. 用户手动重命名时写入 `title_source=manual`、`title_locked=true`，后续自动命名直接跳过。

标题生成使用独立的无工具 LLM 请求，低温度、短输出、严格 JSON；不会把任何工具调用结果写入对话树，也不会改变 Token 压缩逻辑。

## 五、Lane 命名建议流程

1. 用户打开“创建 Lane”，输入可选的方案意图或描述。
2. 前端调用 `POST /api/sessions/{session_id}/lanes/suggestions`。
3. 服务端收集当前 Lane 最近若干条对话摘要、当前 Session 标题和用户输入，发送给 NamingService。
4. NamingService 返回最多 3 个候选，每个候选包括：
   - `name`：可直接用于现有接口和 Git 的 kebab-case slug；
   - `display_name`：面向用户的可读名称；
   - `description`：方案目标说明。
5. 服务端过滤重复名称、保留名、非法 slug，并在候选不足时使用本地规则补齐。
6. 用户点击候选后仍可继续编辑；只有点击“创建 Lane”才真正创建分支。
7. 创建请求把 `name`、`display_name`、`description` 和 `name_source` 一起保存。

建议接口失败时只显示“暂时无法生成建议”，不阻塞用户手动输入名称。Lane 的 Git 创建仍然使用安全 slug，展示名不会进入 shell 命令或文件路径。

## 六、协议与前端展示

### 6.1 REST

| 接口 | 作用 |
|---|---|
| `POST /api/sessions/{id}/lanes/suggestions` | 根据当前上下文生成 Lane 候选 |
| `POST /api/sessions/{id}/lanes` | 接收可选的 `display_name`、`description`、`name_source` |
| `GET /api/sessions/{id}` | Snapshot 返回 Session 标题元数据和 Lane 元数据 |

### 6.2 WebSocket 事件

| 事件 | 关键字段 | 作用 |
|---|---|---|
| `session_title_updated` | `title`、`source`、`locked` | 更新工作台标题 |
| `lane_renamed` | `lane`、`new_lane` | 刷新 Lane 列表和当前选择 |
| `lane_deleted` | `lane` | 刷新 Lane 列表 |

现有 `lane_created`、`lane_switched` 事件增加展示名时仍保留原有 `lane` 字段，不破坏旧客户端。

## 七、失败、边界与安全

- 空消息不触发自动命名；超过最大长度的标题和描述会被截断。
- 手动标题可以是中文；Lane slug 仍严格遵守后端 kebab-case 规则，前端只做体验校验，后端仍是最终边界。
- 自动命名调用出现异常只记录日志并降级，不改变 `RunResult` 状态；Session 删除时会取消尚未完成的后台命名任务。
- LLM 返回 Markdown 代码块、额外解释或非法 JSON 时，服务端只提取安全 JSON；提取失败使用本地降级。
- 命名提示词只传递必要的会话内容，不传 API Key、权限请求、回滚数据和工作区外路径。
- 命名功能不执行工具、不写代码、不改变当前 Lane，不应绕过权限管理。
