# 12 - 存储层设计

> JSONL 物理格式、加载/写入/崩溃恢复的工程实现

---

## 一、职责边界：这份文档解决什么问题

[02-树形对话历史系统](02-树形对话历史系统.md) 定义了树的数据模型（Entry、parent 指针、查询算法）；[03-Lane分支管理系统](03-Lane分支管理系统.md) 定义了 Lane 指针的语义。这两份文档回答"数据长什么样、怎么查询"。

本文档回答的是另一层问题：**这套数据物理上怎么落盘、进程启动时怎么加载进内存、崩溃后怎么恢复、这套 JSONL 方案的容量上限在哪**——是前两份文档的工程实现细节，不重复设计数据模型。

一个常被问到的问题（也是这份文档存在的直接原因）：**"这么庞大的记忆管理系统，JSONL 文件搞得定吗？"** 结论先给：搞得定——不是因为 JSONL 天生强大，而是因为这个项目的实际数据规模远远够不到 JSONL 会露馅的门槛。第七节给出具体的容量估算作为这个结论的依据。

---

## 二、文件组织

每个 session 对应一组独立的 JSONL 文件，不同 session 之间完全隔离：

```
data/sessions/
  ├── {session_id}.jsonl          # 树形历史（Entry）
  └── {session_id}_lanes.jsonl    # Lane 指针更新流水
```

日志文件（`logs/*.jsonl`）是独立的存储对象，由 [11-日志与可观测性](../04-支撑模块/11-日志与可观测性.md) 管理，不在本层的职责范围内——两者都是 JSONL，但用途、读写模式、生命周期都不同，混在一起管理会让两个系统互相牵连。

---

## 三、Entry 的物理格式

字段语义见 [02-树形对话历史系统](02-树形对话历史系统.md) 第二节，这里只定序列化规格。

| 字段 | 类型 | 是否必需 | 说明 |
|---|---|---|---|
| `id` | string | 是 | UUID4，唯一标识 |
| `parent` | string \| null | 是 | 父节点 id，根节点为 `null` |
| `lane` | string | 是 | 创建归属标签（不是路径信息，见 03 号文档 1.5 节） |
| `seq` | int | 是 | 全局严格递增序号，用于崩溃恢复时校验完整性 |
| `role` | string | 是 | `user` \| `assistant` \| `tool` |
| `content` | string \| list | 是 | 文本，或结构化的 `tool_use`/`tool_result` 块列表 |
| `timestamp` | float | 是 | Unix 时间戳 |

一行一个完整 JSON 对象，UTF-8 编码，`\n` 结尾：

```jsonl
{"id":"e1","parent":null,"lane":"main","seq":1,"role":"user","content":"优化函数","timestamp":1756425600.0}
{"id":"e2","parent":"e1","lane":"main","seq":2,"role":"assistant","content":"建议缓存","timestamp":1756425605.2}
```

**约束（呼应 02 号文档 2.2 节）**：一次 assistant 回复并行调用多个工具时，所有 `tool_result` 必须打包成**一行** Entry 再写入，不能各自单独写一行——否则会在物理文件层面就制造出破坏树结构的数据。

## 四、加载策略：启动时全量加载 + 三个内存索引

JSONL 是 append-only 的，本身不提供任何索引能力。**所有树查询必须走内存索引，绝不允许对 JSONL 文件做线性扫描**——这是从设计第一天就要落地的约束，不是性能优化的可选项。

```python
def load_session(session_id: str) -> "SessionIndex":
    entries: dict[str, Entry] = {}
    children_index: dict[str, list[str]] = defaultdict(list)
    lane_index: dict[str, list[str]] = defaultdict(list)

    path = Path(f"data/sessions/{session_id}.jsonl")
    with open(path, "r", encoding="utf-8") as f:
        for lineno, line in enumerate(f, start=1):
            entry = _parse_line_defensively(line, lineno)  # 见第六节
            if entry is None:
                continue
            entries[entry["id"]] = entry
            if entry["parent"] is not None:
                children_index[entry["parent"]].append(entry["id"])
            lane_index[entry["lane"]].append(entry["id"])

    return SessionIndex(entries, children_index, lane_index)
```

启动后，`get_entry`/`get_children`/`get_lane_entries` 全部是 O(1) 字典查询，文件只在追加新 Entry 时被再次触碰，不参与任何读路径。

## 五、写入策略

### 5.1 追加即写，不做原地重写

```python
def append_entry(session_id: str, entry: dict):
    path = Path(f"data/sessions/{session_id}.jsonl")
    with open(path, "a", encoding="utf-8") as f:
        f.write(json.dumps(entry, ensure_ascii=False) + "\n")
        f.flush()
```

JSONL 只支持追加，不支持原地修改某一行——这正是它"崩溃安全"的来源：已经追加完成的行不会因为后续写入失败而损坏，风险只集中在"正在写的最后一行"（见第六节）。

### 5.2 并发写入序列化

[03-Lane分支管理系统](03-Lane分支管理系统.md) 7.3 节定的"单 Lane 互斥执行"模型，在存储层用一个 session 级别的锁落地：

```python
class SessionStorage:
    def __init__(self, session_id: str):
        self._write_lock = asyncio.Lock()  # 整个 session 只有一个写锁

    async def append_message(self, entry: dict) -> dict:
        async with self._write_lock:
            append_entry(self.session_id, entry)
            self._update_indices(entry)
        return entry
```

不需要更复杂的机制（比如按 Lane 分别加锁）——因为业务规则已经保证任意时刻只有一个 Run 在执行，这一个全局锁本身就是"单 Lane 互斥"决策在存储层的直接体现，不是额外增加的复杂度。

### 5.3 Lane 指针文件同样是 append-only

`{session_id}_lanes.jsonl` 每次 `update_lane` 都追加一行，不是原地覆盖：

```jsonl
{"lane":"main","leaf_id":"e2","seq":1,"timestamp":1756425605.2,"created_from":null}
{"lane":"algo","leaf_id":"e2","seq":1,"timestamp":1756425610.0,"created_from":"e2"}
{"lane":"main","leaf_id":"e7","seq":2,"timestamp":1756425615.0,"created_from":null}
```

同一个 lane 名字会在文件里出现很多次（几乎每条消息都触发一次 `update_lane`）。这个细节直接影响加载逻辑的正确性，见第六节。

## 六、崩溃恢复：两个容易被忽略的正确性问题

### 6.1 半截 JSON 行的防御性解析

如果进程在 `f.write(...)` 执行到一半被杀掉，重启后读到的**最后一行**可能是不完整的 JSON，`json.loads` 会抛异常。加载逻辑必须对此做防御，不能让一整个 session 因为最后一行损坏而完全加载失败：

```python
def _parse_line_defensively(line: str, lineno: int) -> Optional[dict]:
    line = line.strip()
    if not line:
        return None
    try:
        return json.loads(line)
    except json.JSONDecodeError:
        logger.warning(f"跳过损坏的日志行 #{lineno}（可能是崩溃时的半截写入）")
        return None
```

已成功写入磁盘的历史行不受影响，只有"正在写的那一行"存在风险，且这一行本身就代表一次尚未完成的操作，丢弃它是正确的语义（相当于这次 append 没有发生过）。

### 6.2 Lane 指针的"重放语义"，不能只读最后一行

因为 `lanes.jsonl` 是 append-only 的，同名 lane 会重复出现多次。**加载时必须重放全部行，同名 lane 以最后一次出现的记录为准**——不能天真地认为"文件最后一行就是当前状态"，因为文件的物理最后一行可能是**另一个** lane 刚刚被更新产生的：

```python
def load_lanes(session_id: str) -> dict[str, "LanePointer"]:
    lanes: dict[str, dict] = {}  # 重放过程中不断覆盖，天然实现"最后一行生效"
    path = Path(f"data/sessions/{session_id}_lanes.jsonl")
    with open(path, "r", encoding="utf-8") as f:
        for lineno, line in enumerate(f, start=1):
            record = _parse_line_defensively(line, lineno)
            if record is None:
                continue
            lanes[record["lane"]] = record   # dict 赋值天然做到"同名覆盖，取最后一次"
    return lanes
```

这个文件体量很小（每行几十字节），不需要压缩或分文件，但加载逻辑必须按"重放"而不是"取尾行"来写，否则在多 Lane 场景下会读到错误的 leaf_id。

## 七、容量评估：这套方案撑得住吗

这是"JSONL 搞得定吗"这个问题的具体答案。按实际使用场景估算：

- 一个 session 对应一棵树、一个 JSONL 文件（不是全局共享的大文件）。
- 子 Agent 内部的中间消息**根本不落这个文件**（见第八节），只有最终摘要落一条 Entry——这个设计本身就是在替存储层减负。
- 一次真实的 demo 任务：树上大致是几十到几百个节点（每轮问答链条 3~5 个节点，加若干次分叉）。每个节点几百字到几千字，单个 session 文件大概几百 KB 到几 MB。
- 压力测试场景（远超一个人在工期内能跑出来的规模）：1 万个节点，文本量约 10~20MB，Python 进程启动时一次性读入、建好三个字典索引，耗时是毫秒级的。

**结论**：全量加载进内存不是权衡取舍后的妥协方案，而是这个数据规模下完全免费的操作。JSONL 没有索引这个理论短板，在这个项目的规模级别里根本没有被暴露的机会。真正值得花心思的不是"要不要换存储"，而是第六节的两个正确性细节（崩溃恢复、Lane 重放语义）。

**JSONL 真正会露馅的场景**（不是本项目的场景）：多租户生产系统需要跨 session 检索聚合；单个 session 大到无法一次性装进内存；需要跨进程/跨机器的事务保证。这几条都不是这次的问题，[01-系统架构概览](../01-系统架构概览.md) 里"JSONL 而非 SQLite"的决策依据依然站得住。

## 八、子 Agent 的存储边界

[15-子Agent系统](../03-Agent核心层/15-子Agent系统.md) 里的 `EphemeralMessageProvider` 用的是纯内存 list，**完全不经过本层**——不落盘、不进这两个 JSONL 文件、不参与索引构建。子 Agent 循环结束后，临时消息列表直接被 GC 回收（或者选择性地写进独立的调试日志文件，但那是 [11-日志与可观测性](../04-支撑模块/11-日志与可观测性.md) 的职责，不是 SessionStorage 的职责）。

这条边界是故意的：子 Agent 存在的意义就是把大量试错性的中间步骤从主线存储里隔离出去，如果图省事直接复用 `SessionStorage.append_message` 来存子 Agent 的中间消息，等于把子 Agent 机制的核心价值实现反了。

## 九、备选方案与升级路径

如果未来场景变成多租户/需要跨 session 查询（本项目不需要），迁移路径是：

1. 现有 JSONL 文件本身就是"事件日志"，可以整体读入后批量 `INSERT` 到 SQLite
2. `SessionStorage` 的对外接口（`append_message`/`get_entry`/`get_children`）保持不变，只替换内部实现
3. 不需要停机迁移或双写过渡——JSONL 文件可以作为 SQLite 的"源数据"离线导入一次

这个迁移路径不需要在本项目里实现，只是确认当前方案不是死胡同——如果评委问"以后要扩展怎么办"，这里有明确答案。

## 十、测试要点

| 测试场景 | 验证什么 |
|---|---|
| 崩溃恢复：手动截断文件最后一行 | 加载不抛异常，前面完整的行都能正常恢复 |
| 并发写入：模拟同一 session 两次 `append_message` 几乎同时发生 | 写锁生效，两行都完整写入，没有交错 |
| Lane 重放：连续多次 `update_lane` 同一个 lane 名 | 加载后拿到的是最后一次更新的 `leaf_id`，不是文件物理上的最后一行内容 |
| 容量压力：生成 1 万条 Entry 的 session | 加载耗时在可接受范围内（毫秒级），验证第七节的估算 |
