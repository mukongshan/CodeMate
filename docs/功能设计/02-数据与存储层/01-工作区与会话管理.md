# 01 - 工作区与会话管理

> 当前实现基线：2026-09-02
>
> 本文描述 CodeMate 当前已经落地的 `Workspace → Session → Lane` 分级模型、持久化目录、生命周期和旧数据迁移。它取代草稿目录中的“工作区-会话-Lane 分级管理重构方案”作为正式功能设计。

## 一、领域模型

CodeMate 将用户的本地项目目录、一次持续的 Agent 工作和一次对话分支分别建模：

| 对象 | 身份 | 主要职责 | 是否拥有用户源目录 |
|---|---|---|---|
| Workspace | `workspace_id` | 规范化本地目录、维护 Session 归属和显示名称 | 否，只保存路径引用 |
| Session | `session_id` | 保存一次完整对话、权限配置、记忆和 Lane 集合 | 否，使用 Workspace 的路径 |
| Lane | `lane_id` + 兼容 slug `lane` | 指向对话树叶子，并在 Git 可用时绑定代码工作树 | 否，main 可映射源目录，其他 Lane 映射托管 Worktree |
| Entry | `id` | 保存树形对话中的一条 message | 否 |

层级关系固定为：

```text
Workspace
└── Session
    ├── main Lane
    ├── feature Lane
    └── experiment Lane
```

`Workspace` 解决“这个项目有哪些会话”，`Session` 解决“这次工作保存了什么”，`Lane` 解决“在同一会话中从哪个对话和代码状态继续”。三者不允许互相替代：会话数据目录不是用户项目目录，Lane 工作树也不是会话日志目录。

## 二、Workspace 生命周期

### 2.1 创建与去重

创建工作区时，服务端会展开用户路径、解析为规范绝对路径并确认它是目录。同一规范路径只注册一个 Workspace；重复创建返回已有记录并标记 `created=false`。Workspace 使用随机稳定 UUID，路径变化不会改变其身份。

工作区记录包含：

| 字段 | 说明 |
|---|---|
| `workspace_id` | 稳定身份，不用于推导磁盘路径 |
| `path` | 规范化绝对路径 |
| `title` | 用户可读名称，默认使用目录名 |
| `session_ids` | 该 Workspace 下的 Session 顺序列表 |
| `created_at` / `updated_at` | 注册记录时间 |

### 2.2 重命名、缺失和移除

- 重命名只修改注册表中的 `title`，不移动用户目录，也不修改 Session 数据。
- 路径暂时不存在时，Workspace 仍可出现在列表中，状态为 `missing-dir`；服务端不会替用户创建或删除该目录。
- 默认移除只删除 Workspace 注册记录，不删除用户目录、不删除 Session 数据目录。
- 只有显式请求 `cascade=true` 时才级联删除其 Session；级联删除仍遵守 Session 的 Git 清理规则。

## 三、Session 生命周期

### 3.1 创建、加载和列表

Session 可以通过指定 `workspace_id` 创建，也兼容旧式请求中的 `workspace` 路径。未指定 Workspace 时，服务端会将当前配置的 `WORKSPACE` 注册为 Workspace，再创建 Session。

Session 创建后立即拥有 `main` Lane；空会话的 `leaf_id` 为 `null`，第一条用户消息追加后才推进到真实 Entry。列表接口返回展示标题、更新时间、所属 Workspace 和是否已加载到内存；打开 Session 时才构建 `SessionRuntime`。

### 3.2 标题元数据

Session 标题保存在 `session.json`：

| 字段 | 值 | 语义 |
|---|---|---|
| `title` | 字符串 | 当前展示标题 |
| `title_source` | `default` / `manual` / `auto` / `fallback` | 标题来源 |
| `title_locked` | 布尔值 | 手动重命名后锁定自动更新 |
| `title_updated_at` | Unix 时间戳或空 | 最近更新时间 |

创建时传入标题即视为手动标题并锁定。没有标题时先使用 Session ID；首个 Run 成功完成后，后台 `NamingService` 使用首条需求和最终回复生成标题。LLM 失败或返回非法 JSON 时使用本地确定性降级标题，不影响原 Run。手动重命名通过 `PATCH /api/sessions/{session_id}` 完成，并会通过 WebSocket 推送 `session_title_updated`。

### 3.3 删除

删除 Session 是跨资源操作，顺序如下：

1. 写入删除 Journal，状态为 `prepared`。
2. 取消延迟检查点和后台命名任务，释放运行时引用。
3. 清理该 Session 管理的非 main Lane Worktree、托管分支和 Git Binding。
4. Journal 更新为 `git_cleaned`。
5. 从 Workspace 的 `session_ids` 中摘除 Session，删除 Session 数据目录。
6. 全部成功后删除 Journal；异常时记录 `failed` 和可恢复阶段。

启动时 `SessionManager` 会扫描删除 Journal：已经完成 Git 清理但目录删除未完成的操作会自动继续；无法安全判断的操作保留给人工重试。删除过程绝不递归删除用户源工作区，也不会删除已发布的普通 Git 分支。

## 四、磁盘布局

假设配置中的数据根目录为 `data`，当前 Session 布局如下：

```text
data/
├── workspaces/
│   ├── registry.json
│   └── {workspace_id}/
│       └── sessions/
│           └── {session_id}/
│               ├── session.json
│               ├── conversation/
│               │   └── entries.jsonl
│               ├── lanes.jsonl
│               ├── git/
│               │   ├── bindings.json
│               │   ├── checkpoints.ndjson
│               │   └── operations.ndjson
│               └── logs/
└── deletions/
    └── *.json
```

文件职责如下：

| 文件 | 格式 | 保存内容 | 写入策略 |
|---|---|---|---|
| `registry.json` | JSON | Workspace 注册表、顺序和待处理变更 | 原子覆盖 |
| `session.json` | JSON | Session 归属、标题、权限黑名单、时间元数据 | 原子覆盖 |
| `entries.jsonl` | JSONL | Entry 树事实记录 | 追加写入 |
| `lanes.jsonl` | JSONL | Lane 指针和当前 Lane 的事件流水 | 追加写入并重放 |
| `bindings.json` | JSON | Lane 与 Git Worktree/ref 的当前绑定 | 当前状态覆盖 |
| `checkpoints.ndjson` | NDJSON | 代码检查点历史 | 追加写入 |
| `operations.ndjson` | NDJSON | Git 发布、集成、删除等操作记录 | 追加写入 |
| `logs/` | JSONL | 结构化运行日志 | 追加写入 |

`SessionPaths` 集中生成上述路径，业务代码不应自行拼接 Session 文件名。旧版扁平路径仍只作为显式迁移输入，不是新数据的写入位置。

## 五、注册表与一致性

`registry.json` 保存 `version=1`、`workspace_order`、`workspaces` 和 `pending_mutation`。写入采用临时文件、刷新和替换，避免进程中断留下半个 JSON。

加载时对每个 Workspace 的 `session_ids` 做二次校验：Session 元数据中的 `workspace_id` 和规范化 `workspace` 路径必须同时匹配注册表，只有通过校验的 Session 才重新挂回列表。注册表损坏时会备份为 `registry.corrupt-*.json`，再从现有 Session 元数据重建可识别的 Workspace 记录。

## 六、旧数据迁移

旧版本将 `{session_id}.jsonl`、`{session_id}_lanes.jsonl`、Git 元数据和 Session 元数据平铺在 `data/sessions/`。当前迁移是显式、可观察的两步操作：

1. `GET /api/storage/legacy-migration` 生成迁移计划，不修改文件。
2. `POST /api/storage/legacy-migration` 执行复制、大小校验、写入新元数据、挂接 Workspace，成功后才删除旧文件。

迁移目标是 `data/workspaces/{workspace_id}/sessions/{session_id}/`。复制期间发生错误时保留旧文件，并删除不完整的新目录；模块导入和应用启动不会静默迁移。旧 Entry/Lane JSONL 的内容格式保持兼容，缺少新标题或 Lane 展示字段时使用默认值。

## 七、边界与不变量

- Workspace 删除不等于删除用户目录。
- Session 数据目录不等于 Lane 工作目录。
- `main` Lane 在 Git 启用时使用用户源目录；其他 Lane 使用 CodeMate 管理的独立 Worktree。
- 非 Git 工作区仍支持完整对话树和 Lane 指针，但代码隔离、检查点、发布和 Git 对比能力降级并返回原因。
- Session 内 Agent Run 串行，同一时刻只有一个 Lane 执行；切换、删除和压缩等结构性操作会检查运行状态。
- Lane 的 `lane` slug 为兼容身份和 API 路径；展示名称另存，不通过改显示名称移动文件或 Git 资源。

## 八、公开管理接口

| 功能 | 接口 |
|---|---|
| 列出/创建 Workspace | `GET/POST /api/workspaces` |
| 重命名/移除 Workspace | `PATCH/DELETE /api/workspaces/{workspace_id}` |
| 列出/创建 Workspace 内 Session | `GET/POST /api/workspaces/{workspace_id}/sessions` |
| 兼容创建/列出 Session | `POST/GET /api/sessions` |
| 获取/重命名/删除 Session | `GET/PATCH/DELETE /api/sessions/{session_id}` |
| 预览/执行旧数据迁移 | `GET/POST /api/storage/legacy-migration` |

Lane、文件、Git 和实时事件的接口分别见 [03-Lane 分支管理系统](03-Lane分支管理系统.md)、[12-存储层设计](12-存储层设计.md) 和 [08-VSCode 风格会话工作台](../05-Web-UI层/08-VSCode风格会话工作台.md)。
