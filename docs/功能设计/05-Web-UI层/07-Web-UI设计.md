# 07 - Web UI 设计

> 交互式树形可视化与实时对话界面：三个亮点的展示窗口

---

## 一、设计目标与原则

树形历史、Lane 分支、子 Agent 编排——这三个后端亮点如果只活在数据结构里，评委根本感知不到它们存在。前端的职责不是"把界面做得好看"，而是**让这三样东西被看见、被点、被对比**。围绕这个定位，四个要求缺一不可：

| 要求 | 具体体现 |
|---|---|
| **强交互** | 树上的每个节点可点击、可右键、可拖拽；分支可一键创建/切换/对比；不是只能看的静态图 |
| **强可观测** | 任意时刻，用户能看清"Agent 现在在干什么"——包括父 Agent 主循环、子 Agent 内循环、权限等待，三者的状态都不能是黑箱 |
| **强反馈** | 每一次操作都有即时的视觉响应：流式文字、加载动画、成功/失败提示、路径高亮变化 |
| **美观** | 统一的颜色系统、克制的动效、一致的间距与圆角，而不是拼凑的组件堆砌 |

**范围边界**：本文档只覆盖树形历史 / Lane / 子 Agent / Agent 主循环这四个模块的前端呈现。日志的历史查询 UI 已在 [项目设计策略-深挖与打磨](../../草稿/项目设计策略-深挖与打磨.md) 第六章明确降为非亮点、砍掉——本文档的"可观测"指的是**运行时状态的实时呈现**（第九节会明确划这条边界），不是重建一个日志查看器。

## 二、整体布局

```
┌──────────────────────────────────────────────────────────────────┐
│  Toolbar：[● main ▾] [+ 创建分支] [⇄ 对比分支] [Agent: 空闲]      │
├───────────────────────────────┬────────────────────────────────────┤
│                               │                                    │
│   树形历史可视化（40%）        │   对话与观测面板（60%）             │
│                               │                                    │
│   · React Flow 渲染的树       │   · 流式对话消息                   │
│   · 当前 Lane 路径高亮        │   · 工具调用卡片                   │
│   · 分叉点标记                │   · 子 Agent 执行卡片               │
│   · 点击节点 → 详情侧栏       │   · 权限确认弹窗（浮层）            │
│                               │   · 输入框                         │
│                               │                                    │
└───────────────────────────────┴────────────────────────────────────┘
```

左侧是树（结构视图），右侧是当前 Lane 路径的线性重放（内容视图）——两者渲染的是同一份数据的两种投影：左边回答"整体探索到了哪里"，右边回答"当前这条线上具体说了什么"。点击左侧任意节点，右侧滚动定位到对应消息；这个联动是整个界面里最重要的一次交互，必须做得跟手、无延迟。

## 三、颜色系统

颜色在这个界面里只承担两个语义角色，刻意不做第三个用途，避免同一个视觉通道被过度复用而让人看不懂：

- **分类色（categorical）**：标识"这是哪个 Lane"——用在节点边框、连接线、Lane 选择器
- **状态色（status）**：标识"这次操作处于什么状态"——pending / success / error / warning，用在工具调用卡片、子 Agent 卡片、权限弹窗

**节点角色（user/assistant/tool/子Agent）不占用颜色通道，改用图标+形状区分**（见第四节 4.2）。如果角色也用颜色编码，会和 Lane 的分类色抢同一个视觉通道，用户看到一个绿色节点时无法判断"绿色代表 algo 分支还是代表这是个 assistant 消息"——这是色彩编码里典型的通道过载问题，本设计从源头上避免它。

### 3.1 Lane 分类色（固定顺序分配，不循环）

采用经过 CVD（色觉缺陷）验证的默认分类色板，按 Lane **创建顺序**固定分配，不循环复用：

| 分配顺序 | 色名 | 色值 | 典型用途 |
|---|---|---|---|
| 1（默认 main） | blue | `#2a78d6` | 主分支 |
| 2 | orange | `#eb6834` | 第一条分叉 |
| 3 | aqua | `#1baf7a` | 第二条分叉 |
| 4 | yellow | `#eda100` | 第三条分叉 |

这四个槽位是同时在场景中激活的 Lane 数量的实用上限——超过 4 条同时高亮的 Lane，前两个槽位之外的颜色区分度会明显下降（相邻色对的 CVD Delta E 会跌破安全阈值）。**超过 4 条 Lane 时的处理**：非当前高亮的 Lane 统一降级为中性灰 `#898781`，只有用户主动选中/对比的 Lane 才获得彩色高亮——这不是功能缺失，而是"当前关注的东西才需要被强调"这一原则的直接体现。

Lane 选择器下拉里，未激活对比的 Lane 也可以全部平铺展示，只是不需要都占用独立色相。

### 3.2 状态色（固定语义，不可挪用）

| 状态 | 色值 | 用途 |
|---|---|---|
| `pending`（进行中） | `#eda100` + 旋转动画 | 工具/子Agent 执行中 |
| `success`（成功） | `#0ca30c` | 执行成功 |
| `warning`（警告） | `#fab219` | 需要注意但未失败（如子Agent因预算耗尽给出 partial 结论） |
| `error` / `critical`（失败） | `#d03b3b` | 执行失败 |

状态色**永远搭配图标+文字**，不单独用颜色表达状态（这一条是硬规则，不是建议）——色弱用户或黑白打印场景下，仅靠色相无法分辺 warning 和 pending。

### 3.3 界面基础色调

只做亮色一套。**不实现暗色模式**——演示在桌面浏览器进行，一套配色够用；维护两套色值要对每个组件重复校验对比度，投入和收益不成比例。

```css
.app-root {
  color-scheme: light;
  --surface-1:       #fcfcfb;   /* 主背景 */
  --surface-2:       #f9f9f7;   /* 卡片/面板背景 */
  --text-primary:    #0b0b0b;
  --text-secondary:  #52514e;
  --text-muted:      #898781;
  --border:          rgba(11, 11, 11, 0.10);
  --gridline:        #e1e0d9;   /* 树形图背景网格 */
}
```

色值仍然全部走 CSS 自定义属性，不散落在组件里硬编码——这样将来真要加暗色只是多一组变量覆盖，但本次不做。

### 3.4 一个具体的难点：分叉点之前的公共祖先段怎么上色

[实现难点-以dsh为参考](../../草稿/实现难点-以dsh为参考.md) 第六章 6.3 节指出：分叉点之前的节点同时是多条 Lane 路径的祖先，不能简单按 `Entry.lane` 字段单色渲染。具体的视觉方案：

- 节点边框默认是**中性灰**（未被任何高亮路径覆盖时）
- 当前高亮的 Lane 路径经过该节点时，边框换成该 Lane 的分类色
- 如果**多条**当前高亮的 Lane 路径都经过该节点（典型情况：对比两个分支时，公共祖先段同时属于两条路径），边框渲染成**等分的多色环**（比如两条高亮 Lane，边框一半是 main 的蓝色、一半是 algo 的橙色），而不是把两种颜色混合调出一个新色——颜色混合会产生一个不属于任何 Lane 的"第三种颜色"，反而制造歧义。多色环是离散的、可读的，混色不是。

## 四、树形可视化组件

### 4.1 技术选型

React Flow，理由与取舍记录在 [01-系统架构概览](../01-系统架构概览.md) 6.3 节（开箱即用的拖拽/缩放/自动布局，优先功能完整性而非视觉极致定制）。自动布局用 dagre（`direction: 'TB'`）。

### 4.2 节点结构：颜色管分类，图标管角色，环管状态

```
┌─────────────────────────────┐
│ 🤖  Agent · 12:03            │  ← 图标 = 角色（user 👤 / assistant 🤖 / tool 🔧 / 子Agent 🕵️）
│ 我建议用 LRU 缓存优化...      │  ← 内容摘要（截断至 ~50 字）
│ ● main                       │  ← 边框色 = 归属 Lane（展示用，见 03 号文档 1.5.2 节）
└─────────────────────────────┘
   ▲ 边框整圈用 Lane 分类色；右上角小圆点用状态色（仅工具/子Agent节点才有）
```

- **user**：图标 👤，右对齐气泡（对齐右侧对话面板的消息方向）
- **assistant**：图标 🤖，左对齐
- **tool**：图标 🔧，附带工具名（如 `read_file`），状态环随执行状态变化（pending 旋转 → success 绿 / error 红）
- **子 Agent**（`delegate_task` 节点）：图标 🕵️，视觉上比普通 tool 节点略大一号，因为它在语义上是"折叠了一整个子循环"的特殊节点，理应比一次毫秒级的 `read_file` 调用更显眼。详情见 4.5 节。

### 4.3 分叉点标记

一个节点的子节点数 > 1，即为分叉点。除了自然呈现的"一分二"连线形状外，分叉点节点右下角加一个 🔀 小徽标，让用户在缩小视图时也能一眼扫到"这里发生过分叉"，不需要放大才能看清连线数量。

### 4.4 路径高亮逻辑

- 当前活跃 Lane 的路径（从根到该 Lane 的 leaf）始终高亮：节点边框着色、连线加粗且带流动动画
- 用户在分支对比视图里选中的第二条 Lane，同样高亮，用它自己的分类色
- 非高亮路径上的节点：边框降级为中性灰、连线变细，但**不隐藏**——探索过的历史不会因为不在当前焦点就消失，这正是树形历史"无损"的可视化体现

高亮的计算方式：拿到 Lane 的 `leaf_id`，沿 `parent` 指针向上走到根，把路径上出现的节点 id 收集成一个集合，渲染时按集合做样式判断。这一步逻辑必须复用 [02-树形对话历史系统](../02-数据与存储层/02-树形对话历史系统.md) 的 `get_history_path`，不能在前端自己维护一份平行的路径推导逻辑。

### 4.5 子 Agent 执行卡片（亮点二、三的协同点）

子 Agent 内部可能跑 8 轮才返回结果，这段时间它对应的树节点必须持续展示"进行中"，不能让用户觉得卡死：

```
┌────────────────────────────────────┐
│ 🕵️ 子 Agent · [●pending 旋转]        │
│ 任务：检查 calculate_price 的调用方  │
│ ├─ 已用 3/8 步                       │
│ └─ [查看实时进度 ▾]                  │
└────────────────────────────────────┘
      ↓ 完成后
┌────────────────────────────────────┐
│ 🕵️ 子 Agent · [✓success]             │
│ 结论：共 3 处调用，订单模块有类型     │
│       不匹配风险                     │
│ [展开详情] → 用了 5 次工具，读了 3   │
│             个文件，耗时 4.2s        │
└────────────────────────────────────┘
```

这里直接对应 [15-子Agent系统](../03-Agent核心层/15-子Agent系统.md) 第七节的双通道汇报设计：卡片主体展示 `content`（给父 LLM 的精简结论），"展开详情"展示 `details`（工具调用次数、涉及文件——只给人看，不占父 LLM 的 token）。子 Agent 内部的中间步骤（grep/read 的具体过程）**不会**展开成父树上的多个节点，只在这一张卡片内部以一个可选的"实时进度"抽屉呈现，呼应 [15-子Agent系统](../03-Agent核心层/15-子Agent系统.md) 第二节"折叠子 Agent 内部过程"的设计。

并发跑多个子 Agent 时，每张卡片带独立的 `subagent_id`，互不干扰（对应第六节事件契约里的字段）。

### 4.6 交互操作

| 操作 | 触发方式 | 效果 |
|---|---|---|
| 查看详情 | 单击节点 | 右侧对话面板滚动定位；左侧弹出节点详情侧栏（完整内容、时间戳、Token 数） |
| 创建分支 | 右键节点 → "从此处创建分支" | 弹出对话框，用户手动输入 kebab-case 分支名 |
| 回溯 | 右键节点 → "切换到此处" | 树上该节点成为当前 Lane 的新落脚点，右侧对话面板刷新为该路径 |
| 拖拽 | 鼠标拖动节点 | 手动调整布局，不影响数据 |
| 缩放/平移 | 滚轮 / 拖拽画布 | React Flow 内置，`fitView` 按钮一键归位 |

### 4.7 增量布局：避免流式增长时的跳动

对话在实时进行时，树在不断长出新节点。如果每次新增节点都触发 dagre 的全量重新布局，已经渲染好的节点会突然挪位置，视觉上很跳——这是 [实现难点-以dsh为参考](../../草稿/实现难点-以dsh为参考.md) 6.1 节点名的具体问题。

**处理原则**：新节点插入时，只计算新节点自身及其直接父节点局部的位置调整，不重新排布已经稳定下来的历史节点。全量重新布局只在两种情况下触发：用户手动点击"整理布局"按钮，或者一次性加载一个全新的历史 session（此时没有"已渲染的旧节点"需要保持稳定）。

## 五、对话面板

### 5.1 消息气泡

```tsx
// user：右对齐，蓝色背景（不与 Lane 分类色冲突——用固定的中性蓝，不随 Lane 变化）
<UserBubble>{content}</UserBubble>

// assistant：左对齐，浅灰背景；流式时文字逐字追加 + 闪烁光标
<AssistantBubble streaming={isStreaming}>
  {content}
  {isStreaming && <Cursor blink />}
</AssistantBubble>
```

### 5.2 工具调用卡片

```
┌──────────────────────────────┐
│ 🔧 read_file        [●success]│
│ src/main.py                   │
│ [展开查看完整输出 ▾]           │
└──────────────────────────────┘
```

默认折叠，只显示工具名、关键参数、状态；展开后显示完整参数和返回内容。状态图标复用 3.2 节的状态色规范。

### 5.3 子 Agent 卡片

与树节点上的卡片是同一份数据的另一处渲染（对话面板里的版本承担主要交互，树节点上的版本承担"这里存在一次委托"的空间定位），具体样式见 4.5 节。

### 5.4 流式显示的实现要点

```typescript
socket.on('text_delta', ({ messageId, text }) => {
  appendToMessage(messageId, text)  // 追加，不重新渲染整个消息列表
})
```

节流：`text_delta` 事件可能每秒到达数十次，UI 更新用 `requestAnimationFrame` 或轻量节流（~60ms）合并渲染，避免每个字符都触发一次 React 重渲染导致掉帧。

## 六、事件契约：先定 Schema，再写代码

[实现难点-以dsh为参考](../../草稿/实现难点-以dsh为参考.md) 6.2 节明确建议：WebSocket 事件契约要在写前端代码之前定下来，否则前后端会互相打补丁。以下是这套契约的最小完整集合：

| 事件 | 方向 | 关键字段 | 用途 |
|---|---|---|---|
| `node_added` | server→client | `id, parent, lane, role, content` | 树上新增一个 Entry |
| `text_delta` | server→client | `messageId, text` | assistant 消息流式追加 |
| `tool_call_start` | server→client | `callId, toolName, args` | 工具开始执行 |
| `tool_call_end` | server→client | `callId, status, result` | 工具执行完毕（status: success/error） |
| `subagent_started` | server→client | `subagentId, parentCallId, task` | 子 Agent 开始执行（长任务，与普通 tool_call 区分） |
| `subagent_progress` | server→client | `subagentId, step, maxSteps` | 子 Agent 内循环进度（可选，用于卡片的"已用 x/8 步"） |
| `subagent_done` | server→client | `subagentId, status, content, details` | 子 Agent 完成，双通道结果 |
| `lane_created` | server→client | `lane, fromId` | 新建分支 |
| `lane_switched` | server→client | `lane, leafId` | 当前活跃分支变化 |
| `permission_request` | server→client | `requestId, toolName, args, riskLevel` | 需要用户确认（对接 [09-权限控制系统](../04-支撑模块/09-权限控制系统.md) 4.1 节） |
| `permission_response` | client→server | `requestId, action` | 用户的确认结果 |
| `run_error` | server→client | `runId, error` | 主循环级错误 |
| `send_message` | client→server | `content, lane` | 用户发送新消息 |

区分 `tool_call_*` 和 `subagent_*` 是关键决策——子 Agent 是"长时间挂起的工具调用"，如果和普通 `read_file` 共用一套事件，前端没法区分"该展示旋转的 loading 图标"还是"该展示带步数进度的子 Agent 卡片"，这正是 [实现难点-以dsh为参考](../../草稿/实现难点-以dsh为参考.md) 5.3 节指出的问题在协议层的落地。

## 七、分支管理面板

### 7.1 顶部工具栏

```tsx
<Toolbar>
  <LaneSelector value={currentLane} onChange={switchLane} />
  <Button onClick={createBranch}>+ 创建分支</Button>
  <Button onClick={compareBranches}>⇄ 对比分支</Button>
  <AgentStatusBadge state={agentState} />  {/* 空闲 / 运行中 / 等待权限确认 / 错误 */}
</Toolbar>
```

`AgentStatusBadge` 是可观测性的第一入口——不需要打开任何面板，一眼就能看到 Agent 当前处于四种状态里的哪一种。

### 7.2 分支对比视图

左右分栏，各自展示一条 Lane 从公共祖先之后的独有部分（复用 [03-Lane分支管理系统](../02-数据与存储层/03-Lane分支管理系统.md) 第四节的 `compare_lanes` 结果）。如果两个 Lane 当前恰好指向同一叶子（03 号文档 1.5.4 节提到的边界情况），对比视图直接提示"两个分支尚无差异"，不渲染两个空白栏——避免制造出一个没有意义的对比结果。

### 7.3 创建分支对话框

一个文本输入框，用户手动输入 kebab-case 名称，前端按 [03-Lane分支管理系统](../02-数据与存储层/03-Lane分支管理系统.md) 的命名规则做即时校验（非法字符、重名、保留名 `main`），校验不通过时禁用确认按钮并就地提示原因。不做 LLM 命名建议（[14-技术决策与取舍](../06-项目管理/14-技术决策与取舍.md) 已否决）。

## 八、权限确认与错误反馈

### 8.1 权限确认

完整的确认对话框设计见 [09-权限控制系统](../04-支撑模块/09-权限控制系统.md) 4.2 节，本文档不重复——但需要强调一点交互原则：权限请求到达时，**不能打断用户正在读的内容**，弹窗以浮层出现在对话面板上方，用户看完当前上下文后再决策，弹窗本身不自动消失、不设倒计时。

### 8.2 错误反馈：分两级

- **轻量错误**（工具执行失败、网络抖动）：Toast 浮层，3 秒自动消失，附带"重试"快捷操作
- **需要关注的错误**（权限被拒绝导致中断、API 调用彻底失败）：常驻的 Alert 卡片嵌入对话流中（不是弹窗打断），带明确的错误原因和建议操作，用户读完再自行关闭

两级的区分标准：**是否需要用户做出后续决策**。仅仅告知状态用 Toast，需要用户看清楚原因再决定下一步的用 Alert。

## 九、可观测性面板的范围：与"被砍掉的日志 UI"划清边界

[项目设计策略-深挖与打磨](../../草稿/项目设计策略-深挖与打磨.md) 第六章明确把"日志实时查询 UI"降为非亮点、直接砍掉——那是指**历史日志的检索/过滤/分析界面**（对应 [11-日志与可观测性](../04-支撑模块/11-日志与可观测性.md) 第七节的 LogViewer 组件），用 `cat logs/agent.jsonl` 或简单脚本查询即可，不值得投入前端工作量。

本文档强调的"强可观测"是另一件事：**运行时状态的实时呈现**，且这件事本身就是树形可视化和对话面板的自然产出，不需要额外的一整套查询界面：

- Agent 当前在跑哪个阶段 → `AgentStatusBadge`（7.1 节）
- 工具调用的进度和结果 → 工具卡片（5.2 节）
- 子 Agent 的内部进展 → 子 Agent 卡片（4.5 节）
- 权限决策的等待状态 → 权限弹窗（8.1 节）
- 探索过的所有历史路径 → 树形图本身（第四节）

这五样东西加起来已经覆盖了"用户能看清 Agent 在干什么"的全部需求，不需要再造一个独立的日志检索页面。

## 十、动效规范

动效服务于"强反馈"，但要克制，不能变成为了炫技而炫技：

| 场景 | 动效 | 时长 |
|---|---|---|
| 新节点出现 | 从透明+缩小 0.8 → 正常，ease-out | 200ms |
| 高亮路径的连线 | 流动的虚线动画（只在当前活跃路径上） | 循环 |
| 分支切换 | 对话面板内容渐隐渐显，不是硬切 | 150ms |
| Toast 出现/消失 | 从底部滑入/滑出 | 200ms |
| 权限弹窗 | 淡入 + 轻微缩放 | 150ms |

所有动效遵守 `prefers-reduced-motion` 系统设置，用户开启该项后动效降级为瞬时切换，不强迫任何人接受动画。

```
前端框架: React 18 + TypeScript
状态管理: Zustand
树形可视化: React Flow + dagre（自动布局）
UI 组件: Shadcn UI
样式: Tailwind CSS（配合第三节的 CSS 变量做主题切换）
通信: WebSocket（原生或 Socket.IO，按后端 FastAPI 的实现选择）
图标: Lucide React
```

## 十二、性能与实现约束

- **不需要虚拟化列表**：按 [12-存储层设计](../02-数据与存储层/12-存储层设计.md) 第七节的容量估算，单个 session 的节点数在几十到几百量级，React Flow 和普通消息列表都能直接全量渲染，不必引入虚拟滚动的额外复杂度
- **`text_delta` 节流**：见 5.4 节，避免逐字符触发重渲染
- **增量布局**：见 4.7 节，避免流式场景下的布局跳动

## 十三、响应式设计（P2，非重点）

桌面端左右分屏是主要形态，评委演示大概率在桌面浏览器进行。移动端/平板适配（Tab 切换树形图和对话）作为时间允许再做的加分项，不投入核心工期。

## 十四、实现优先级

**P0（必须）**：
- 左右分屏布局、React Flow 树形渲染、WebSocket 事件契约落地（第六节）
- 流式对话显示、基础工具调用卡片
- Lane 切换、当前路径高亮

**P1（重要）**：
- 分叉点标记、节点点击详情侧栏
- 分支创建/对比对话框
- 子 Agent 执行卡片（4.5 节、5.3 节）
- 权限确认弹窗、错误 Toast/Alert 两级反馈

**P2（加分）**：
- 增量布局优化的精细打磨、拖拽手动调整
- 动效细节打磨（十节全部动效）
- 响应式布局

**不做**：暗色模式（3.3 节）、智能分支命名建议（7.3 节）、日志历史查询 UI（第九节）。全项目范围的优先级见 [13-项目跟踪](../06-项目管理/13-项目跟踪.md)，本节只覆盖前端部分。
