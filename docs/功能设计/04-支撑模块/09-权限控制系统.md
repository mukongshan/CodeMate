# 3 级权限模型与用户确认流程

---

## 一、当前实现

权限系统现在是一个工具入口门禁，不是分散在每个工具里的散点校验。

- `SAFE` 工具自动放行：`read_file`、`glob`、`grep`、`list_directory`、`web_search`、`web_fetch`、`delegate_task`
- `WRITE` 工具按路径判定：工作区内自动放行，系统关键路径直接拒绝，工作区外请求用户确认
- `DANGEROUS` 工具按命令判定：先做静态安全检查，再看命令黑名单；命令安全且未命中黑名单时自动放行，命中黑名单时直接拒绝，其余安全检查失败的情况请求用户确认
- 所有需要确认的操作都通过 WebSocket 发送 `permission_request`
- 用户响应通过 `permission_response` 回来，支持 `allow_once` / `allow_always` / `deny`
- 当前“沙箱”不是容器隔离，而是权限门禁 + 路径约束 + `subprocess` 执行约束

门禁实现集中在 `backend/src/permission/manager.py`，纯规则函数放在 `backend/src/permission/rules.py`，便于单测独立覆盖。

## 二、权限级别

```python
from enum import Enum

class PermissionLevel(str, Enum):
    SAFE = "safe"
    WRITE = "write"
    DANGEROUS = "dangerous"
```

`TOOL_PERMISSIONS` 的当前映射如下：

| 工具 | 级别 | 处理方式 |
|---|---|---|
| `read_file` | SAFE | 自动放行 |
| `glob` | SAFE | 自动放行 |
| `grep` | SAFE | 自动放行 |
| `list_directory` | SAFE | 自动放行 |
| `web_search` | SAFE | 自动放行 |
| `web_fetch` | SAFE | 自动放行 |
| `write_file` | WRITE | 路径检查 |
| `edit_file` | WRITE | 路径检查 |
| `bash` | DANGEROUS | 命令安全检查 + 黑名单 + 用户确认 |
| `delegate_task` | SAFE | 自动放行 |

未登记工具默认按 `DANGEROUS` 处理，策略是保守，不是放行。

## 三、PermissionManager

`PermissionManager` 负责一次工具调用的最终裁决。

```python
class PermissionManager:
    def __init__(self, workspace: str | Path, config: dict | None = None): ...
    async def check(self, tool_name: str, args: dict) -> PermissionDecision: ...
    def get_command_blacklist(self) -> list[str]: ...
    def set_command_blacklist(self, commands: list[str]) -> list[str]: ...
```

实际流程：

1. 读取工具级权限
2. 检查用户既有决策记忆
3. `SAFE` 直接放行
4. `WRITE` 进入路径校验
5. `DANGEROUS` 进入命令安全检查
6. 需要人工确认时，通过 `ask_user_callback` 发起 WebSocket 询问
7. 没有确认回调时，默认拒绝

`PermissionDecision` 记录三类信息：

- `allowed`
- `reason`
- `user_confirmed` / `auto_approved`

`audit_log` 会记录每次决策，供调试和审计使用。

## 四、写入路径检查

`WRITE` 级别不会一概询问用户，而是分三层判断：

1. 没有 `path` 参数，直接拒绝
2. 命中系统关键路径，直接拒绝
3. 路径在工作区内，自动放行
4. 路径在工作区外，询问用户确认

路径安全的纯函数在 `rules.py`：

- `is_safe_path(path, workspace)`
- `is_system_path(path)`

这里用的是“工作区内”与“系统关键路径”双重判断，不依赖字符串前缀碰撞。

---

## 五、命令检查与黑名单

`DANGEROUS` 级别的 bash 命令不是直接拒绝，而是先做静态安全检查：

- 命中危险模式直接视为不安全
- 包含命令替换的表达式不做自动放行
- `cd` 到工作区外会被识别
- 常见写入、删除、覆盖命令会检查目标路径是否越界

然后再看命令黑名单：

- 命令安全
- 且未命中黑名单
- 就自动放行

命中黑名单直接拒绝；只有未命中黑名单但存在 workspace 越界等其他安全风险时，才进入用户确认。

相关函数：

- `inspect_command_safety(command, workspace)`
- `is_command_blacklisted(command, blacklist)`
- `normalize_command_blacklist(commands)`

黑名单通过 session 级接口维护，并由启动配置提供默认值。

---

## 六、用户确认接口

当前 WebSocket 确认流是：

1. 服务端发 `permission_request`
2. 前端弹出确认 UI
3. 用户返回 `permission_response`
4. `allow_once` 只放行当前操作
5. `allow_always` 进入记忆列表
6. `deny` 进入拒绝记忆列表

确认请求的风险级别使用 `low` / `medium` / `high`，由 `PermissionLevel` 映射而来。

---

## 七、配置与接口

命令黑名单来自两处：

- 启动配置 `COMMAND_BLACKLIST`
- session 级权限门禁接口

接口如下：

- `GET /api/sessions/{session_id}/permissions/gate`
- `PUT /api/sessions/{session_id}/permissions/gate`

前端会在会话快照里恢复 `command_blacklist`，因此门禁状态可以跟着 session 走。

---

## 八、安全边界

当前实现的边界是：

- 读操作自动放行
- 写操作先卡路径
- 命中黑名单的命令直接拒绝
- 其他安全命令自动放行；额外安全检查失败时才请求确认
- 子 Agent 复用父 Agent 的同一个 `PermissionManager`

这套机制解决的是“工具门禁”，不是完整容器沙箱。
