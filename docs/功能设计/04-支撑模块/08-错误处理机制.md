# 错误捕获、传播与处理机制

---

## 一、当前实现

当前系统把错误分成三层：

1. 工具层错误
2. run 级错误
3. 请求 / 协议层错误

对应的承载方式也不同：

- 工具层用 `ToolResult`
- run 级用 `AgentError` + `run_error`
- 请求 / 协议层用 WebSocket `error` 或 HTTP 响应

这意味着“出错”不等于“中断整个 Agent”。

---

## 二、工具层：ToolResult

`backend/src/tools/base.py` 里的 `ToolResult` 是当前真实结果类型：

```python
class ToolResult:
    content: str
    is_error: bool
    metadata: dict
    suggestions: list[str] | None
```

规则很简单：

- `is_error = False` 时，`content` 直接喂给 LLM
- `is_error = True` 时，`to_llm_text()` 会把建议一起带回去
- `metadata` 只给前端和日志，不进入 LLM 上下文

工具执行失败、参数校验失败、权限不足，最终都会收敛成 `ToolResult` 回给 LLM。

---

## 三、run 级错误：AgentError

`backend/src/errors/types.py` 里统一使用异常体系：

- `ToolExecutionError`
- `PermissionDeniedError`
- `ValidationError`
- `LLMAPIError`
- `SystemError`
- `SessionNotFoundError`
- `LaneNotFoundError`

`AgentError` 带有稳定的 `code` 和 `message`，并可转成两种输出：

- `to_llm_text()`：给模型看的文本
- `to_api_dict()`：给 API / 前端看的结构化字段

当前主循环里，`AgentError` 会触发：

- `state = error`
- 发送 `run_error`
- 返回 `RunResult(status="error")`

---

## 四、事件级别的区别

`error` 和 `run_error` 不是同一个层次。

### `error`
请求级、协议级错误。典型场景：

- WebSocket 消息格式不对
- 连接层收到非法 payload
- 不能把请求正确解析成指令

### `run_error`
一次 run 的失败反馈。典型场景：

- LLM 调用失败
- 工具执行失败且被提升为 run 级错误
- 后端内部异常

`run_error` 当前会带这些字段：

- `run_id`
- `code`
- `message`
- `error`
- `retryable`
- `suggestions`

---

## 五、主循环中的传播路径

当前传播链路大致是：

1. 工具执行入口先做权限检查
2. 参数校验失败或工具执行失败时，返回 `ToolResult`
3. `ToolResult` 作为 `tool` 消息回给 LLM
4. `LLMAPIError` 和未预期异常会把当前 run 推到 error 状态
5. `run_error` 发给前端

因此，普通工具失败是“可继续迭代”的，不会像系统崩溃一样直接打断整个会话。

---

## 六、用户可见反馈

前端现在会同时显示两类反馈：

- 对话流里的错误卡片
- 工具栏里的运行状态和连接状态

所以用户不需要靠看日志判断 Agent 卡在哪一步。

---

## 七、REST 与 WebSocket 的差异

当前 REST 层对 `AgentError` 仍是统一映射到 HTTP 400，未做更细粒度的状态码拆分。

WebSocket 层则更细：

- 请求 / 协议问题走 `error`
- 运行问题走 `run_error`

这也是为什么前端不能只盯 HTTP 状态码看结果。
