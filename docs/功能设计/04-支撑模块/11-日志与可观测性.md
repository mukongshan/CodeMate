# 11 - 日志与可观测性

> 基于当前源码的实现说明，基线日期：2026-09-02。

## 一、定位与边界

日志系统服务于后端诊断和运行追踪。它记录 Agent、工具、会话管理和协议层的关键事件；前端实时反馈由 `SessionRuntime`/WebSocket 事件通道单独负责。

当前实现**不包含**独立的日志查询页面、日志筛选 API、日志轮转和自动清理策略。运行过程的用户可见反馈主要来自 WebSocket 事件与工作台状态，不要求用户打开日志文件排查普通执行进度。

## 二、存储位置

采用 Workspace → Session 分级目录时，日志位于：

```text
data/
└── workspaces/{workspace_id}/sessions/{session_id}/
    └── logs/
        ├── {session_id}_agent.jsonl
        └── permissions.jsonl
```

兼容旧扁平存储时，`StructuredLogger` 仍可使用配置中的 `LOG_DIR`；新建 Session 优先使用该 Session 的 `logs/` 目录。

| 文件 | 内容 | 写入方式 |
|---|---|---|
| `{session_id}_agent.jsonl` | Agent 生命周期、Run、工具、记忆、检查点和异常等结构化事件 | 追加写入，一行一个 JSON 对象 |
| `permissions.jsonl` | `StructuredLogger.log_permission_decision()` 的独立审计输出；当前主权限流程尚未自动写入 | 追加写入，一行一个 JSON 对象 |

日志文件不是对话历史的权威来源。对话内容写入 `conversation/entries.jsonl`，Lane 写入 `lanes.jsonl`，Git 检查点和操作写入 `git/` 下的 NDJSON 文件。

## 三、结构化日志模型

普通事件由 `StructuredLogger` 统一生成，字段如下：

| 字段 | 含义 |
|---|---|
| `timestamp` | 本地时间的 ISO 8601 字符串 |
| `session_id` | 事件所属 Session |
| `level` | `DEBUG`、`INFO`、`WARNING` 或 `ERROR` |
| `event` | 稳定的事件名称 |
| 其他字段 | 与事件相关的结构化数据 |

日志采用 JSONL，使用 UTF-8 和 `ensure_ascii=False` 写入；字段值无法直接序列化时使用字符串兜底，单条日志写入失败只记录标准库告警，不改变主流程结果。

### 3.1 事件范围

事件名称由 Agent、SessionRuntime 和 WebSocket 层共同使用，重点覆盖：

| 事件范围 | 典型内容 |
|---|---|
| Agent 生命周期 | `agent_started`、状态变化、运行结束 |
| Run 执行 | Run 开始、完成、失败、取消、达到迭代上限 |
| 工具调用 | 工具开始、结果、异常、权限决策 |
| 文件审查 | 文件变更、接受或拒绝审查结果 |
| 记忆与上下文 | 压缩、摘要落盘失败、预算相关状态 |
| Session 管理 | 自动命名、删除清理、检查点延迟刷新失败 |
| 协议与连接 | WebSocket 连接、断开、非法消息和事件推送失败 |

事件表的作用是统一命名和定位问题，不代表每个事件都会在前端显示为独立日志卡片。

### 3.2 前端实时事件

当前 WebSocket 连接通过 `SessionRuntime.set_emitter()` 接收运行事件；这条通道不读取 `{session_id}_agent.jsonl`。`StructuredLogger.ui_callback` 虽然保留了回调扩展点，但当前 WebSocket 入口没有把它接入前端推送。

前端消费的是运行协议事件，例如 `run_started`、`run_completed`、`run_error`、`tool_call_start`、`tool_call_end`、`permission_request`、`file_review` 和子 Agent 进度事件。它们与日志事件可能相关，但两者不是同一个持久化数据模型。

## 四、权限审计

权限决策由 `PermissionManager` 作出。当前主流程通过 `PermissionManager._audit()` 把审计条目保存在运行时内存，并由审计接口返回；`StructuredLogger` 提供了 `log_permission_decision()` 文件写入方法，但当前代码没有把该方法接入每次权限决策。因此，`permissions.jsonl` 是现有日志器支持的输出格式，不应被描述为当前每次权限决策都会产生的持久化文件。

| 字段 | 含义 |
|---|---|
| `tool` | 被检查的工具名 |
| `args` | 脱敏后的工具参数 |
| `allowed` | 是否允许执行 |
| `reason` | 决策原因 |
| `user_confirmed` | 是否经过用户确认 |
| `auto_approved` | 是否由安全规则自动批准 |

后端提供以下权限审计与规则接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/sessions/{session_id}/permissions/audit` | 返回当前权限管理器的审计报告 |
| `GET` | `/api/sessions/{session_id}/permissions/gate` | 读取命令黑名单 |
| `PUT` | `/api/sessions/{session_id}/permissions/gate` | 更新命令黑名单 |

审计接口返回的是当前权限管理器维护的内存报告；它不是通用 JSONL 日志检索接口。Session 重启后，这份内存审计不会从 `permissions.jsonl` 自动恢复。

## 五、敏感信息处理

写入前会递归处理字典字段。字段名忽略大小写，命中以下敏感键时替换为 `***`：

`api_key`、`apikey`、`password`、`token`、`secret`、`authorization`。

该规则覆盖普通结构化事件和权限审计参数，但不是完整的数据分类系统。新增事件时应优先记录路径、大小、状态和摘要，避免把完整文件内容、提示词、密钥或访问令牌放入日志。

## 六、控制台与错误隔离

标准库 `logging` 由 `setup_logging()` 配置：

- 调试模式使用 `DEBUG`，普通模式使用 `INFO`。
- `WARNING` 和 `ERROR` 级别的结构化事件同时输出到标准库日志。
- `httpx` 和 `openai` 的日志级别提升到 `WARNING`，减少模型请求噪声。
- 日志文件写入失败不会覆盖 Agent 结果，只产生标准库告警；运行事件推送失败也由 WebSocket 层单独处理。

Agent 结果与日志持久化明确解耦。比如自动检查点失败会记录告警，但不把已经完成的 Run 改成失败；同样，WebSocket 客户端断开不会要求日志器抛出异常。

## 七、诊断路径

发生问题时按以下顺序定位：

1. 先看工作台的运行状态、错误卡片、工具卡片和权限提示，确认问题属于连接、Run、工具还是权限层。
2. 再查看对应 Session 的 `{session_id}_agent.jsonl`，按 `timestamp`、`level`、`event` 和 `run_id` 关联事件。
3. 如果是权限行为，查看 `permissions.jsonl` 或调用权限审计接口。
4. 如果是对话、Lane、Git 或文件版本问题，分别查看它们各自的事实存储，不用日志替代事实数据。

当前没有统一的日志查看器；Windows 环境可用文本工具查看 JSONL，Linux/WSL 环境可使用 `cat`、`jq` 等本地工具进行临时分析。

## 八、实现映射

| 代码位置 | 职责 |
|---|---|
| `backend/src/observability/logger.py` | `StructuredLogger`、Agent JSONL 写入、脱敏、标准库桥接，以及可选的权限审计文件写入 |
| `backend/src/api/session_service.py` | 为 Session 注入日志目录，记录运行、命名、检查点和管理事件 |
| `backend/src/api/ws.py` | 连接生命周期、协议错误和实时事件转发 |
| `backend/src/permission/manager.py` | 权限决策、命令黑名单和内存审计报告 |
| `backend/src/api/routes.py` | 权限审计与命令规则 REST 接口 |
| `backend/src/storage/workspace_storage.py` | 生成 Session `logs/` 路径并创建目录 |

## 九、当前限制与后续方向

当前明确保留的限制：

- 没有日志轮转、容量上限和自动清理，长期运行时需由部署环境自行管理磁盘。
- 没有独立日志检索 UI；前端以实时运行事件为主。
- 普通日志没有独立的 REST 查询接口，不能把 JSONL 当作在线查询数据库。
- 没有跨 Session 的集中式日志聚合和指标系统。

后续若实现这些能力，应先定义容量、保留期、权限和脱敏策略，再扩展存储与 UI；不能仅在前端读取日志文件来绕过后端权限边界。

## 十、验证范围

现有后端测试覆盖权限审计 API；日志器本身提供脱敏和 JSONL 写入实现。文档变更本身使用 Markdown 链接检查和标题结构检查验证，不替代后端测试。
